# Граф денег

Локальный инструмент для первичной AML-проверки транзакционной сети. По трём обезличенным parquet-файлам он строит направленный граф, присваивает каждому `gid` объяснимую роль, делит сеть на сообщества и выдаёт список клиентов для углублённой проверки. Роль означает **структурную гипотезу**, а не причастность к преступлению.

## Запуск одной командой

Нужен Python 3.10+ и доступ к PyPI при первом запуске. Из корня репозитория:

```bash
./run.sh
```

Скрипт создаёт локальное окружение, устанавливает зависимости из `requirements.txt` и запускает полный пересчёт. Папка `data/` должна содержать `nodes.parquet`, `edges.parquet`, `transactions.parquet`. Другой путь можно передать так: `./run.sh --data /path/to/data --out /path/to/out`.

В Windows (PowerShell), при установленном Python 3.10+:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe run.py
```

Если окружение `.venv` уже подготовлено, достаточно последней команды.

Результат находится в `out/`: три обязательные выгрузки `nodes_roles.csv`, `clusters.csv`, `top_nodes.csv`, дополнительные `cycles.csv`, `timeline.csv`, `resilience.csv`, `data_gaps.csv` и автономная страница `network.html`. Откройте HTML в браузере как обычный файл. Интернет и сервер для просмотра не нужны. На предоставленных 2 248 узлах прямой расчёт `run.py` занимает менее секунды на тестовой машине; установка пакетов в это время не входит. Целевой предел пересчёта — 5 минут.

## Сценарий аналитика

1. Запустить `./run.sh` после помещения выгрузки в `data/`.
2. Открыть `out/network.html`, найти `gid` из списка правоохранительных органов или из топа слева.
3. Переключиться на один или два шага связей, изучить направление стрелок, суммы и карточку узла. Переключить окраску между ролями и кластерами.
4. Использовать `top_nodes.csv` как очередь углублённой проверки; `evidence` и числовые поля `nodes_roles.csv` позволяют проверить каждый вывод.
5. Сверить `attention` у выбранных узлов и сформировать запрос на недостающие данные по `data_gaps.csv`.
6. Уточнить связи вопросом ассистенту: `assistant.py "кто собирает деньги с этих пятерых: …"`.

## Схема решения

![Схема пайплайна](architecture.svg)

Граф направленный: ребро `src → dst` означает перевод от отправителя получателю. `edges.parquet` сверяется с суммами и количеством операций в `transactions.parquet`. Все узлы из `nodes.parquet`, включая изолированные seed, остаются в результате.

Обязательные поля не допускают пропусков. Идентификаторы, глубина и число операций должны иметь целочисленный тип, `is_seed` — булев тип. Суммы должны быть конечными положительными числами; допустимое расхождение агрегата с транзакциями — не более 0,01 KZT на пару. Пустой список узлов отклоняется с сообщением об ошибке. Перед построением графа узлы и рёбра сортируются для воспроизводимости при перестановке строк входных файлов.

## Формальные правила ролей

`in_deg` — число разных плательщиков, `out_deg` — число разных получателей. `in_kzt` и `out_kzt` — только видимые внутри выгрузки суммы. `seed_reach` — количество seed, из которых узел достижим по направлению переводов за максимум четыре ребра. `bridge` — нормированное посредничество на направленном графе, оценённое по 96 фиксированным источникам (`seed=42`). `rapid_48h` — доля входящих операций, после которых у того же узла есть исходящая операция в следующие 48 часов; это временной сигнал, не сопоставление конкретных денег.

Правила применяются в указанном порядке; первое выполненное правило задаёт основную роль:

| Роль | Условие |
|---|---|
| `coordinator` | Не seed; `seed_reach ≥ 3`, `in_deg ≥ 3`, `bridge` не ниже 90-го процентиля **положительных** значений в текущей выгрузке. Кандидат на координирующий узел, не идентификация организатора. |
| `distributor` | `out_deg ≥ 8` и `out_deg ≥ 2 × max(in_deg, 1)`. |
| `consolidator` | `in_deg ≥ 4` и `in_deg ≥ 2 × max(out_deg, 1)`. |
| `transit` | Не seed; есть вход и выход, `0.8 ≤ out_kzt / in_kzt ≤ 1.2`. Сравнение сумм остаётся приблизительным из-за неполной видимости. |
| `terminal` | Не seed; `in_deg > 0`, `out_deg = 0`, `depth < 4`. Это только наблюдаемый конечный получатель в границах выборки. |
| `peripheral` | Остальные узлы, в том числе обрыв на 4-м колене без исходящих. |

`role_score` лежит в диапазоне 0–1 и отражает силу выполнения выбранного **правила**: базовое значение 0.60 растёт с запасом по числу связей, seed и близостью доли пропуска к единице; для терминалов базовое значение 0.62, для граничной периферии 0.55. Это эвристическая оценка, **не калиброванная вероятность**. Точные формулы находятся в `score_roles()` в [run.py](run.py).

Для каждого `gid` поле `evidence` содержит числа, на которых основана роль, и не превышает 200 символов. Дополнительные колонки в `nodes_roles.csv` позволяют разобрать любой узел за минуту. Например, для граничного узла пояснение прямо говорит, что исходящие после четвёртого колена неизвестны.

## Кластеры и приоритет

Кластеры вычисляются детерминированным Louvain (`seed=42`) по **ненаправленной проекции** графа с весом `sum_kzt`. Направление сохраняется в исходном графе, ролях, метриках и интерфейсе; проекция используется только для поиска плотно связанных групп. Изолированные узлы получают собственный кластер. `sum_kzt_internal` включает только рёбра, где оба конца в данном кластере. `top_gids` — пять клиентов кластера с наибольшим приоритетом. `hypothesis` описывает наблюдаемый характер группы и требует проверки.

Приоритет — взвешенная сумма процентильных рангов в текущей выгрузке:

```text
base = 0.20·P(in_deg) + 0.20·P(in_kzt) + 0.20·P(seed_reach)
     + 0.20·P(bridge) + 0.15·P(out_deg) + 0.05·rapid_48h
priority_score = base × role_factor × boundary_factor × seed_factor
```

`P` — процентильный ранг признака среди всех узлов с одинаковым значением для совпадающих значений. `role_factor`: coordinator/consolidator/distributor = 1; transit = 0.95; terminal = 0.85; peripheral = 0.75. `boundary_factor = 0.65` для узла на четвёртом колене без исходящих, иначе 1. `seed_factor = 0.85` для известных seed, иначе 1. Итог ограничен диапазоном 0–1. Эти коэффициенты задают очередь проверки, а не оценку вины. `top_nodes.csv` содержит первые 100 строк с ролью, скором и числовым обоснованием; минимум ТЗ — 20.

Чтобы приоритет был проверяемым, `nodes_roles.csv` дополнительно содержит разбор формулы: `priority_base`, вклады `priority_payers`, `priority_incoming`, `priority_seed_reach`, `priority_bridge`, `priority_recipients`, `priority_rapid` и множители `priority_role_factor`, `priority_boundary_factor`, `priority_seed_factor`. Те же числа видны в карточке узла в `network.html`.

| Файл | Содержание |
|---|---|
| `nodes_roles.csv` | Одна строка на каждый входной `gid`; обязательные поля `gid`, `role`, `role_score`, `cluster_id`, `priority_score`, `evidence` и дополнительные проверяемые метрики. |
| `clusters.csv` | Одна строка на сообщество: `cluster_id`, `n_nodes`, `n_seed`, `sum_kzt_internal`, `top_gids`, `hypothesis`. |

| `cycles.csv` | Возвратные потоки: `cycle_id`, `length`, `path`, `bottleneck_kzt`, `n_seed`. |
| `timeline.csv` | Дневная активность по каждому `gid`: входы, выходы, оборот, чистый поток и число уникальных контрагентов за день. |
| `resilience.csv` | Что остаётся от сети после изъятия топ-N узлов по приоритету и N случайных. |
| `data_gaps.csv` | Белые пятна выгрузки: `gap`, `n_nodes`, `meaning`, `next_request`, `example_gids`. |
| `network.html` | Самодостаточный экран с поиском, стрелками, фильтром кластеров, окраской ролей, топ-листом и карточками узлов с флагами внимания и дневной активностью. |

`gid` — синтетический идентификатор. В интерфейсе он передаётся строкой, чтобы JavaScript не терял точность 64-битного числа. В CSV это целочисленный идентификатор.

## Дополнительные сигналы

Эти признаки закрывают опциональные пункты ТЗ. Они **не меняют** роль и приоритет, а попадают в колонку `attention` (`nodes_roles.csv`, `top_nodes.csv`) и в карточку узла. Так каждый флаг проверяется отдельно и не смешивается с правилами ролей. Если флагов нет, в `attention` записано `нет`.

| Признак | Колонка | Как считается | Флаг в `attention` |
|---|---|---|---|
| Возвратные потоки | `cycles`, `cycle_with_seed` | простые направленные циклы длиной ≤ 4 перевода (`nx.simple_cycles`); список — в `cycles.csv`, `bottleneck_kzt` — минимальная сумма на ребре цикла | узел лежит хотя бы на одном цикле |
| Всплески активности | `timeline.csv` | входящие и исходящие переводы агрегируются по календарному дню и `gid` | показываются в карточке узла как самые активные дни |
| Синхронные входы | `sync_payers_max` | максимум разных плательщиков в один календарный день | ≥ 3 |
| Дробление | `repeat_amount_max` | сколько раз узел отправил одну и ту же сумму | ≥ 4 |
| Суммы у порога | `near_threshold_in` | входящие переводы 5 000–9 999 KZT | ≥ 3 и не меньше половины входящих |
| Выброс для колена | — | `in_deg` выше 99-го процентиля своего колена | при `in_deg ≥ 3` |
| Скрытый выход | `p_hidden_outgoing` | см. ниже | ≥ 50%: «продлить обход» |

**Обрыв 4-го колена.** Обход раскрывает исходящие всех узлов колен 0–3, поэтому у них `p_hidden_outgoing = 0`. Для 444 узлов 4-го колена исходящие не выгружались. Их вероятность оценивается эмпирически: какая доля не-seed узлов колен 1–3 с тем же числом плательщиков (1, 2, 3–4, 5+) имеет исходящие. На текущей выгрузке это 29% для одного плательщика, 57% для двух и 73% для 3–4. Так 434 граничных узла с одним плательщиком ближе к настоящим конечным получателям, а 10 узлов с 2+ плательщиками стоит раскрыть дальше в первую очередь. Все граничные узлы остаются `peripheral`: оценка задаёт очередь дозапроса, а не роль.

**Устойчивость сети.** `resilience.csv` сравнивает изъятие топ-N по `priority_score` с N случайными узлами (`seed=42`). `seed_reach_share` — доля пар «seed → узел в пределах 4 переводов», которые остались связаны. На текущей выгрузке изъятие топ-10 оставляет 74% таких пар и 70 связных фрагментов, топ-50 — 47%; 50 случайных узлов — 96%. Значит, приоритет действительно выделяет узлы, на которых держится сеть.

**Белые пятна.** `data_gaps.csv` перечисляет, чего не хватает в выгрузке, сколько узлов это затрагивает и какой запрос сделать следующим: продление обхода от граничных узлов, входящие и межбанковские переводы seed без исходящих, переводы ниже 5 000 KZT для узлов с суммами у порога, источники для узлов, которые отдали больше, чем получили, и для фрагментов вне основной компоненты.

## AI-ассистент аналитика

Вопрос на естественном языке превращается в ответ по графу со ссылками на `gid`:

```bash
# Один раз задайте адрес внутреннего или локального OpenAI-compatible endpoint:
export OPENAI_BASE_URL=http://127.0.0.1:8000/v1
export OPENAI_MODEL=my-local-model
# export OPENAI_API_KEY=...  # только если внутренний endpoint требует токен

.venv/bin/python assistant.py "Кто собирает деньги с 100000000437046100, 100000000331309100 и 100000008346837100?"
.venv/bin/python assistant.py            # диалог с уточняющими вопросами
.venv/bin/python assistant.py --offline "..."   # без обращения к API
```

Также параметры можно передать явно: `assistant.py --base-url http://127.0.0.1:8000/v1 --model my-local-model "..."`.

**Как устроено.** Модель за локальным или внутренним OpenAI-compatible Chat Completions API только планирует запросы и пишет ответ. Каждый факт она берёт из детерминированных инструментов `graph_tools.py`, которые работают на том же графе и тех же ролях, что `run.py`:

| Инструмент | Что возвращает |
|---|---|
| `node_profile` | роль, место в очереди, метрики, `evidence`, `attention` |
| `counterparties` | прямые плательщики и получатели с суммами |
| `shared_counterparties` | кто получает деньги от нескольких `gid` (downstream) или платит им (upstream) в пределах N переводов |
| `money_paths` | цепочки переводов от одного `gid` к другому с суммой на каждом шаге |
| `top_nodes` | очередь приоритетов с фильтром по роли, кластеру, флагам |
| `cluster_summary` | размер, seed, внутренний оборот, роли и лидеры кластера |
| `node_cycles` | возвратные потоки через узел |

Системная инструкция требует ссылаться только на данные инструментов, писать `gid` полностью, формулировать выводы как гипотезы и учитывать ограничения выгрузки. Инструменты выполняются локально и доступны модели как стандартные function tools.

**Доступ.** `OPENAI_BASE_URL` обязателен: приложение не подставляет адрес публичного API и не отправляет данные во внешний сервис автоматически. `OPENAI_MODEL` задаёт имя модели на вашем endpoint. `OPENAI_API_KEY` необязателен и используется только если ваш внутренний шлюз требует авторизацию. Без endpoint, модели или соединения ассистент сообщает об этом и отвечает офлайн: по `gid` в вопросе выбирает один инструмент (один `gid` — профиль и связи, несколько — общие получатели или, при словах «кто платит», «откуда», «источник», общие источники; без `gid` — очередь приоритетов).

## Ограничения интерпретации

- Граф построен только по исходящим переводам от seed на четыре колена. **444 узла на 4-м колене без исходящих не считаются terminal**: это артефакт границы обхода; `p_hidden_outgoing` лишь оценивает вероятность продолжения. У других узлов также могут быть невидимые связи за рамками выгрузки.
- Цикл, синхронность и повтор суммы — структурные совпадения. Они не доказывают, что по цепочке прошли одни и те же деньги.
- Входящие seed из-за пределов выборки не видны. Для seed не применяется правило транзита по отношению `out_kzt / in_kzt`. Нельзя считать это отношение полным балансом и для остальных узлов.
- Переводы ниже 5 000 KZT и операции в других банках отсутствуют. Временной признак не доказывает прохождение одних и тех же средств.
- Клиентских атрибутов и размеченных истинных ролей нет. Числовые пороги и веса являются проверяемыми эвристиками; качество оценивается аналитиком по подтверждённым внешним данным.

## Проверка и демо на 5 минут

После `./run.sh` проверьте число строк и непустые поля командой:

```bash
.venv/bin/python -m unittest discover -s tests -v
```

В Windows: `.\.venv\Scripts\python.exe -m unittest discover -s tests -v`.
Проверка переключения кластеров в интерфейсе (нужен Node.js): `node tests/test_viewer.cjs`.

Для демо: за первую минуту показать запуск и выгрузки; затем открыть топ-1 в HTML и объяснить плательщиков, охват seed и посредничество; найти произвольный `gid` из зала, показать входящие и исходящие связи; открыть один граничный `gid` (`boundary=True`) и объяснить, почему ему не присвоен `terminal`. Завершить кластером с несколькими seed и его гипотезой, затем показать `resilience.csv` (изъятие топ-10 против случайных) и `data_gaps.csv` как план следующего запроса.

## При росте до миллиона узлов

Parquet читать по частям через Polars или DuckDB, хранить агрегаты в колонночном формате и строить сжатое представление смежности. Louvain и посредничество переносить в igraph/graph-tool или распределённый графовый движок; посредничество считать на выборке с заданной погрешностью. Сохранять рассчитанные метрики по батчам и обновлять затронутые компоненты. В браузер отдавать только выбранный кластер или окрестность `gid`, а не миллион узлов сразу. Пороги ролей и формулу ранжирования можно сохранить, но их нужно заново проверить на распределении признаков крупной сети.
